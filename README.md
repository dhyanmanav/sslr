# TamperGuard – Suricata Log Tampering Forensics

TamperGuard is a standalone log-tampering forensic workspace. It watches Suricata's `eve.json`, links every log line into a **SHA-256 hash chain**, stores the baseline in **Supabase**, and re-verifies the file to detect **modified, inserted, deleted or truncated** logs. It also provides controlled manual scenarios, a bounded live packet monitor, account-isolated evidence, chain-of-custody records, and a printable court-style PDF report.

## Setup (5 steps)
1. **Supabase**: create a project → SQL Editor → paste & run `supabase_schema.sql`.
2. Set `SUPABASE_URL`, `SUPABASE_ANON_KEY` (Project Settings → API) and `EVE_PATH` in `.env`.
3. Install Node.js 18+, then: `npm install`
4. Run Suricata (below), then run `npm start` and open http://localhost:3000. The service waits for `eve.json` if Suricata has not started yet.
5. Demo data is optional and is never generated by `npm start`.

## Suricata on Windows
In `suricata.yaml`, under `outputs: - eve-log:` make sure `enabled: yes`, `filename: eve.json` and the types include
`alert`, `http`, `dns`, `tls`, `smtp` (flow/stats are chained for integrity but not displayed).
Run (admin PowerShell): `suricata.exe -c "C:\Program Files\Suricata\suricata.yaml" -i YOUR_LAPTOP_IP`
Default log: `C:/Program Files/Suricata/log/eve.json`. Confirm that this exact path matches `EVE_PATH`; TamperGuard reads the file continuously while Suricata appends events.
Email shows up as SMTP events and TLS/DNS to mail hosts (gmail, outlook, imap/smtp…); websites as http/tls/dns.

## Demo without Suricata
```
$env:DEMO_EVE_PATH = "$PWD\demo-eve.json"
npm run sample           # optional: writes fake lines only to demo-eve.json
npm start                # real mode: only ingests the configured Suricata eve.json
npm run live             # optional demo-only continuous fake writer
node scripts/tamper.js modify 20     # edit demo line 20   -> LINE_MODIFIED
node scripts/tamper.js delete 40     # delete demo line 40 -> LINES_REMOVED
node scripts/tamper.js insert 60     # forge a demo line   -> LINES_INSERTED

```
Then click **Verify now** (auto-verify runs every 30 s). Stop Suricata before tampering with a real file (Windows locks it).

## Safe tamper-detection demonstration

### Attack while Suricata is running

This is the recommended demonstration for the project agenda. Keep Suricata and TamperGuard running, wait until the dashboard shows `LIVE`, then modify a previously ingested line in place:

```powershell
npm run attack:live -- 20
```

The command changes line 20 without changing its byte length or replacing the file. Suricata can continue appending packets. TamperGuard's next automatic verification, or the **Verify now** button, should report `TAMPERED` and create a `LINE_MODIFIED` alert. Use a line number shown in the Events tab; it must already exist in the recorded baseline.

This live attack is intentionally limited to same-length modification. Do not use the older `insert`, `delete`, or `truncate` commands while Suricata is writing, because those operations rewrite or shrink the evidence file and can interfere with the writer.

### Synthetic alert injection while Suricata is running

For the append-based demonstration used by the project presentation, keep both Suricata and TamperGuard running and execute:

```powershell
npm run attack:synthetic
```

This appends a clearly marked JSON alert to the configured `EVE_PATH`, using the marker `cyberforensics_test_tampered=true`. TamperGuard recognizes this explicit test marker on the next poll, stores the event, and immediately creates a critical `SYNTHETIC_TAMPER_TEST` alert. It will appear in **Integrity alerts**, the dashboard latest-alert panel, and the Court report.

You can also run the equivalent command directly:

```powershell
$p = 'C:\Program Files\Suricata\log\eve.json'
$e = @{
    timestamp = (Get-Date).ToUniversalTime().ToString('yyyy-MM-ddTHH:mm:ss.fffZ')
    event_type = 'alert'
    src_ip = '192.168.1.50'
    dest_ip = '192.168.1.10'
    proto = 'TCP'
    cyberforensics_test_tampered = $true
    alert = @{ action = 'allowed'; gid = 1; signature_id = 999999; rev = 1; signature = 'TEST ONLY - Synthetic tampering test'; category = 'Test Log Integrity Alert'; severity = 1 }
} | ConvertTo-Json -Compress
Add-Content -Path $p -Value $e
```

If Windows returns `EPERM`, use Administrator PowerShell. The marker is intentionally explicit and must only be used for demonstrations; normal Suricata alerts are not treated as tampering.

### Easy live attack simulation through Suricata

The recommended live demonstration does not edit or append to the locked `eve.json`. It makes Suricata detect real TCP SYN traffic using the included test rule.

1. Add the included rule from `rules\tamperguard-test.rules` to the `rule-files` list in `suricata.yaml`:

```yaml
rule-files:
  - tamperguard-test.rules
```

Copy the rule into Suricata's configured rules directory if the YAML uses a different `default-rule-path`, then restart Suricata and TamperGuard.

2. Keep Suricata and TamperGuard running, then from the project directory run:

```powershell
npm run simulate:attack
```

To target another monitored IPv4 address:

```powershell
npm run simulate:attack -- -Target 192.168.1.10 -Port 9999 -Count 10
```

Suricata writes the alert itself, TamperGuard ingests it as a `security` event, and the Overview page shows it under **Active security**. The panel automatically becomes quiet after 60 seconds without a new alert. The permanent record remains available under **Integrity alerts**, verification history, custody, and the Court report.

If Windows reports `EPERM` or `EACCES`, open **PowerShell as Administrator**, change to the project folder, and run the command again:

```powershell
Set-Location "C:\Users\dell\Downloads\tamperguard\tamperguard"
npm run attack:live -- 20
```

If it still fails, Suricata has the file open without allowing concurrent writes. Move the Suricata log directory outside `C:\Program Files` (for example `C:\Suricata\log`), update `EVE_PATH` and Suricata's `eve-log.filename`, restart both programs, and retry. This is the safer Windows configuration for a live tamper demonstration.

To test the dashboard against the current Suricata baseline, stop Suricata first and make a backup:

```powershell
Copy-Item "C:\Program Files\Suricata\log\eve.json" "C:\Program Files\Suricata\log\eve.json.backup"
$env:DEMO_EVE_PATH = "C:\Program Files\Suricata\log\eve.json"
node scripts/tamper.js modify 20
```

Return to the dashboard and click **Verify now**. It should report `TAMPERED` and create a `LINE_MODIFIED` alert. Other demonstrations are:

```powershell
node scripts/tamper.js delete 40
node scripts/tamper.js insert 60
node scripts/tamper.js truncate
```

Restore the evidence file after testing, then restart TamperGuard:

```powershell
Copy-Item "C:\Program Files\Suricata\log\eve.json.backup" "C:\Program Files\Suricata\log\eve.json" -Force
```

Do not run these commands while Suricata is writing to the file. For a completely non-destructive demo, use `DEMO_EVE_PATH` with `npm run sample`, but point `EVE_PATH` to that demo file before starting TamperGuard.

## PDF forensic report

Click **Generate PDF report** in the standalone workspace, then click **Print / Save as PDF** in the report window. In the Windows browser print dialog, choose **Save as PDF** or **Microsoft Print to PDF**. The report includes the case metadata, evidence path, connection state, file size, hash algorithm, genesis hash, chain head, verification history, tamper findings, and chain-of-custody records.

## Log Tampering workspace

The standalone workspace opens directly after sign-in. The controlled Clean, Deleted, Modified, Injected, and Timestamp scenarios exercise the timestamp, deletion-marker, privilege-escalation, and suspicious-access checks. The method selector is retained for presentation, while the backend performs the deterministic integrity checks and reports each finding.

The **Live Suricata packet monitor** accepts `eve.json` or `fast.log`, starts at the current file end, and processes only newly appended records. It keeps bounded in-memory history and summarizes event types, protocols, domains, recent records, website visits, timestamp reversals, malformed JSON, truncation, and the explicit `cyberforensics_test_tampered=true` demonstration marker. Stop the monitor before changing paths or switching log formats.

## Email Security module

Click **Email security** in the header to open the separate real-time email module. It uses only Suricata SMTP metadata already written to `eve.json`; it does not log in to Gmail/Outlook, read mailbox contents, or store message bodies and attachments. It tracks sender, recipients, HELO, protocol endpoints, timestamps, and summaries, retaining only the bounded classified event window.

The module raises explainable `EMAIL_THREAT` findings for suspicious metadata such as social-engineering phrases, disposable sender domains, raw-IP SMTP HELO values, and potentially dangerous attachment names when Suricata exposes those fields. Suricata must have `smtp` enabled in the EVE output, and the machine must be able to observe the SMTP traffic. Encrypted provider traffic may expose only connection metadata rather than message content.

## Link & Redirect Monitor

Click **Link monitor** to open the separate navigation workspace. It polls the classified Suricata web events and explains HTTP 3xx responses, login/account paths, cross-site destinations, and cases where the redirect target is not exposed in the available metadata. It does not inspect encrypted page contents or claim that a redirect is malicious merely because it crosses domains; it reports the evidence that is actually available.

## ESP32 synthetic tamper demonstration

The ESP32 sketch at `examples/esp32_synthetic_attack/esp32_synthetic_attack.ino` produces the same fixed synthetic event as the PowerShell demonstration: `event_type=alert`, `cyberforensics_test_tampered=true`, severity `1`, and signature `TEST ONLY - Synthetic tampering test`. It sends an authenticated request to TamperGuard; the server appends the event to the configured `EVE_PATH`, ingests it, and the dashboard shows the same `SYNTHETIC_TAMPER_TEST` alert.

Before uploading the sketch:

1. Set `ESP32_ATTACK_TOKEN` in `.env` to a long random value and restart TamperGuard.
2. Put the server computer's LAN IP in `TAMPERGUARD_URL`, for example `http://192.168.1.10:3000/api/demo/esp32-attack`.
3. Set the Wi-Fi credentials and the same token in the sketch.
4. Upload and reset the ESP32. After Wi-Fi connects, it sends exactly one event. The server enforces the token and a three-second trigger limit.

This is intentionally a bounded demo trigger, not arbitrary file-write access from the microcontroller. Keep it on a trusted LAN and use it only with an evidence file you own.

## Detection logic
`chain_n = SHA256(chain_{n-1} + SHA256(line_n))` over *every* line. Verification re-walks the file and compares with stored baselines:
modified line → line hash mismatch · hidden edit in unstored lines → chain break · removed/inserted lines → stored hashes found at shifted positions · truncation → fewer lines / smaller file.

## Notes
- Anon-key RLS policies in the SQL are open for demo use; tighten before production.
- `custody_log` and `tamper_alerts` are append-only via DB triggers.
- Backend: Node/Express. API: `/api/status|stats|events|alerts|verifications|custody|report`, `POST /api/verify`, `POST /api/logtamper`, and `/api/logtamper/monitor/start|stop|status`.
- The dashboard retains the newest `MAX_STORED_EVENTS` classified events (default 2,000) and prunes older event details automatically. The cryptographic chain head and full line count remain in `log_sources`; for a live tamper demonstration, choose a line currently visible in **Live events**.
- The **Project team** navigation page identifies G39, the four team members, and the project guide.
- Each Supabase account receives its own evidence source (`account-<user-id>`), verification history, alerts, events, and report. A newly created account starts with a fresh baseline; it does not inherit another account's old tamper status.
- Routine Suricata parser warnings such as `SURICATA IPv4 truncated packet` remain available as security events but are not promoted to Integrity alerts. This prevents noisy medium-severity rows from hiding the live demonstration finding.
